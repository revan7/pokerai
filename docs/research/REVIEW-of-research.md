# Adversarial cross-review of R1–R6

Review date: **2026-09-10**. All six reports were read. This review checks consequential claims against primary documentation, source, papers, release records and license text; it does not certify every inventory entry. No solver was installed, compiled or benchmarked. **Performance, correctness and deployment on the supplied workstation remain not verified.** Quoted report text is identified by report/section. Author benchmarks establish what was reported, not independent replication. Recommendations and arithmetic below are this review's analysis.

**Decision:** a bounded, validated preflop/HU postflop baseline is defensible; an arbitrary live six-max frequencies-plus-EV assistant within 15 seconds is not established. Resolve range acquisition, unsupported pots, action translation and the actual table-side workflow before expanding the UI or exploit layer. R3's blanket rejection of AGPL unnecessarily removes the strongest inspected integration candidate for this private-use scope.

## 1. Factual errors and material misattributions

**F01 — R1 §2.5: the preflop accuracy claim belongs to postflop.**

> “0.016% exploitability at 10K iterations” for the preflop solver.

The DCFR-SOLVER README places 0.016% in its **flop+turn+river** results, with 103K decision nodes. Its six-max preflop section separately reports 100M iterations and a 14-minute runtime. Neither establishes six-player preflop exploitability of 0.016%. R2 §5 identifies this correctly. **Impact:** do not select the experimental preflop engine on a nonexistent accuracy certificate. [DCFR-SOLVER README](https://github.com/exinori/DCFR-SOLVER#the-journey)

**F02 — R1 §5.3: missing flop classes cannot be recovered by isomorphism.**

> “184-flop subset … nearest-isomorph lookup for unsolved flops”

Suit isomorphism preserves ranks and suit relationships. If the actual flop's equivalence class is absent from the subset, there is no equivalent stored flop. Pio's weighted subsets approximate **averages over flops/preflop values**, not exact strategies for every omitted board. Use an exact class match, solve the actual board, or declare a separately validated approximation. A visually similar board is not an isomorph. [Pio's stated subset purpose and validation](https://piosolver.com/blog/2015-11-05-flop-subsets/), [Waugh's isomorphism algorithm](https://www.cs.cmu.edu/~kwaugh/publications/isomorphism13.pdf)

**F03 — R3 §4.1: canonical flop multiplicities are wrong.**

> “number of raw flops it represents (1, 3, 4, 6, 12, 24 depending on suit pattern)”

For unordered three-card boards from a full deck, before conditioning on private cards, the suit-permutation orbit sizes are **4, 12 or 24**, not 1/3/6. Derivation: trips have C(4,3)=4 suit choices; distinct-rank monotone boards have 4; each distinct-rank two-tone placement has 4×3=12; distinct-rank rainbow boards have 4×3×2=24; either paired-board suit pattern has C(4,2)×2=12. Check: 13×4 + 312×12 + 286×(4+3×12+24) = 22,100. These raw counts also differ from optimized weights in a reduced subset and from range-conditioned board probabilities. [Isomorphism basis](https://www.cs.cmu.edu/~kwaugh/publications/isomorphism13.pdf), [Pio subset construction](https://piosolver.com/blog/2015-11-05-flop-subsets/)

**F04 — R3 §§1.1–1.2, 6: Rust `poker` does accept seven-card inputs.**

> “5-card and 3-card only - not 7-card”; “Not suitable for 7-card.”

Version 0.7.0's `Evaluator::evaluate_five` finds the best five-card hand from **at least five supplied cards**, including seven. Five-card hand classification was confused with input-card-count support. This does not establish speed comparable with a specialized seven-card evaluator. [Versioned API contract](https://docs.rs/poker/0.7.0/poker/struct.Evaluator.html#method.evaluate_five)

**F05 — R3 §§1.1–1.2: material qualification to eval7's “exact” API.**

> “Exact” = full enumeration; “hand-vs-range exact + MC”

The API exists as reported; this is an omitted scope restriction, not a false API-existence claim. `py_hand_vs_range_exact` enumerates opponent hands against a **complete five-card board**. Its implementation performs no enumeration of missing community cards. `py_all_hands_vs_range` switches to this path only when the board has five cards and the range is small enough; otherwise it uses MC. It is not an exact flop/turn runout oracle. R3 correctly warns that these equity APIs ignore range weights; retain that warning. [Implementation: `hand_vs_range_exact` and `all_hands_vs_range`](https://github.com/julianandrews/pyeval7/blob/master/eval7/equity.pyx)

**F06 — R1 §§1, 2.6: blanket ACPC exclusion from pip wheels is false.**

> “ACPC/universal_poker needs source build”; “not in the pip wheel per docs/install.md”

The official wheel workflow explicitly sets `OPEN_SPIEL_BUILD_WITH_ACPC=ON` for its Linux/macOS builds. Optional in a source build does not mean absent from every wheel. Windows pip support has a separate beta announcement; the exact Windows wheel's Universal Poker availability was **not verified** here. This correction improves its plausibility as a test/reference environment, not as a 15-second NLHE solver. [Official wheel configuration](https://github.com/google-deepmind/open_spiel/blob/master/.github/workflows/wheels.yml), [Windows pip announcement](https://github.com/google-deepmind/open_spiel/issues/1531)

**F07 — R1 §2.6: GPU-CFR speedup is paired with the wrong workload scale.**

> “up to 203.6× faster … on games up to ~550k nodes”

Kim's 2024 paper reports 203.6× for **Battleship-7, 2,529,949 nodes**. Experiment 1 ends at 549,946 nodes; Experiment 2 extends to 57,920,421. R1 §2.7 gives the larger limit, contradicting its own §2.6. The paper also reports 254.096 seconds of matrix setup for Battleship-7, excluded from iteration throughput. None of these is an NLHE range-solver speedup. [Paper, Tables 6, 7 and 9](https://arxiv.org/html/2408.14778)

**F08 — R5 §2: Electron's current release line is stale.**

> “Electron 43.x per Wikipedia (July 2026 …) — not verified against electronjs.org.”

Official records place 43.0.0 stable on **June 30, 2026**, and 44.0.0 stable on **August 25, 2026**. Thus 44 is the current stable major at the review cutoff; 43 remains a supported older line. R5 properly marked its secondary-source claim unverified, but it should not supply the project's current-version assumption. [Official release schedule](https://releases.electronjs.org/schedule)

**F09 — R5 scorecard/§5: .NET MAUI is not Windows-only.**

> “WinUI 3 / .NET MAUI … Windows-only”

WinUI 3 is Windows-specific; .NET MAUI targets Android, iOS, macOS and Windows, using WinUI 3 on Windows. This is a conflation of a platform UI framework with the cross-platform framework using it. It does not by itself make MAUI the best choice here. [Microsoft's MAUI platform description](https://learn.microsoft.com/en-us/dotnet/maui/what-is-maui?view=net-maui-10.0)

**F10 — R5 recommendation: `utilityProcess` is not a direct native-executable launcher.**

> “`poker-core` compiled as a standalone binary driven over stdio JSON lines (`child_process`/`utilityProcess`)”

`utilityProcess.fork` takes a **script module path** and creates a Node-enabled utility process. It does not directly replace `child_process.spawn` for a Rust `.exe`. A script could launch the executable, but adds another process layer. The proposed Rust sidecar should use an actual executable-spawn API. R5's earlier comparison with `child_process.fork` is correct; its fallback wording drops the distinction. [Electron utility-process API](https://www.electronjs.org/docs/latest/api/utility-process#utilityprocessforkmodulepath-args-options)

**F11 — R5 §6: the UI can use the GPU too.**

> “The UI shell never touches the GPU; the solver crate does.”

WebView2 has a GPU helper process; hardware-accelerated rendering can consume GPU resources independently of CUDA solving. Correct statement: solver compute is architecturally independent of the UI framework. Do not budget all nominal 16 GB as solver-available VRAM or assume a separate solver process isolates a system-wide driver reset. Actual UI/driver memory use is **not verified**. [Microsoft WebView2 process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)

**F12 — R3 §§3, 5, 6: AGPL is wrongly treated as an adoption prohibition for this scope.**

> “License blocker”; “Do not vendor; use only as a spec/reference”; “Skip: postflop-solver (AGPL, suspended)”

AGPL permits private execution and modification. Vendoring is not prohibited. Sharing a covered combined program and operating a modified network-interactive version create obligations, not a blanket ban on use. R1/R6's private baseline recommendation is compatible with this; see C02 and B06 for the important LAN qualification. [AGPL §§0, 2, 5–6, 13](https://www.gnu.org/licenses/agpl-3.0.html)

**Resolved uncertainty, not an original factual error:** R3 says SKPokerEval's license was “not verified” and excludes it. Its accessible `main/LICENSE.md` contains **Apache-2.0**. The failed retrieval should no longer disqualify it on license grounds; performance/maintenance still need separate assessment. [Actual license](https://github.com/kennethshackleton/SKPokerEval/blob/main/LICENSE.md)

## 3. Overclaims, unsupported exclusions and planning assumptions

**O01 — latency certainty increases between R1's evidence and recommendation.** R1 §5.2 says “river < 1 s” and “a modern 16-core should land ~5–8 s”; its evidence contains no target-machine turn/river benchmark. The flop estimate is explicitly labeled extrapolation, so it is not a fabricated measurement. The problem is using it as the delivery budget. The i7-13700K has **8 P-cores + 8 E-cores**, not sixteen equal high-performance cores. All-core scaling, bunching, wide ranges, raises and deep stacks need measurement. End-to-end 5–15 seconds: **not verified**. [Intel specifications](https://www.intel.com/content/www/us/en/products/sku/230500/intel-core-i713700k-processor-30m-cache-up-to-5-40-ghz/specifications.html)

**O02 — historical comparative evidence does not establish current competitiveness.** R1's “Independent benchmark” label appears under TexasSolver; b-inary is independent of TexasSolver, so that attribution is defensible. Its later “Fastest measured CPU engine” claim is explicitly limited to an apples-to-apples spot. Preserve those limits in the recommendation: an engine author's comparison using Desktop 0.2.1, Pio Free 2.0.8 and GTO+ 1.5.0 does not establish current universal superiority. R1 also omits the same source's TexasSolver correctness concern: 63.0% betting versus approximately 55.2% for the others, with unavailable overall EV. That is an unresolved warning, **not proof** TexasSolver is wrong. [Benchmark methodology and results](https://github.com/b-inary/wasm-postflop#comparison)

**O03 — unavailable API is converted into categorical impossibility.** R1 §§2.2, 3: “Cannot be embedded”; “closed GPU products … cannot be embedded.” TexasSolverGPU's distribution notice confirms private source, not technical impossibility of automation or the outcome of a separate license negotiation. Correct status: **no verified supported API or integration rights**. R6's wording is more defensible. GTOpen likewise has no license identified in the inspected root; GitHub `license: null` alone is not a legal audit. [Distribution notice](https://github.com/bupticybee/TexasSolverGPU/blob/main/EULA.md), [GTOpen root](https://github.com/MatthewPDingle/GTOpen), [GitHub license-detection limitations](https://docs.github.com/en/rest/licenses/licenses)

**O04 — GPU memory and speed are extrapolated from incompatible quantities.** R1's “16 GB RTX 5080 can hold roughly that size of tree, not much larger” is not demonstrated by one 7.6-GB figure. Node count alone omits hand counts, arena layout, scratch and precision. Host working set must not be added to device VRAM. The updated GTOpen report explicitly distinguishes the two. RTX 5080 fit/speed under each path remains **not verified**. [Memory definitions and lifecycle measurements](https://raw.githubusercontent.com/MatthewPDingle/GTOpen/master/research/autoresearch/gpu-pass.md)

**O05 — package benchmarks are not interchangeable seven-card API throughput.** R3 labels its entire table “7-card speed,” but PokerKit's cited page identifies a “standard hand” benchmark without sufficiently specifying that workload as end-to-end best-of-seven evaluation. Its ~1.02M/3.23M numbers are faithfully quoted; their classification as comparable seven-card timings and the resulting “~50x” ratio against another machine/C implementation are **not verified**. Sequential native evaluator speed also does not predict random weighted-range MC throughput or Python-call throughput. [PokerKit benchmark](https://pokerkit.readthedocs.io/en/stable/evaluation.html)

**O06 — ecosystem popularity does not establish agent productivity or delivery effort.** R5: “agent output is rarely version-confused,” “both ~50-line adapters,” and “the whole app is a ~10 MB installer.” These are not measured for this product. Its survey citation concerns human language use, not coding-agent reliability. Adapters still need queueing, cancellation, error/version handling and serialization; the actual installer includes whatever sidecars/resources/runtime strategy are selected. Treat the scorecard as judgment, not evidence. [Tauri packaging options](https://v2.tauri.app/distribute/windows-installer/), [Stack Overflow survey's actual subject](https://survey.stackoverflow.co/2025/technology)

**O07 — “only parser” and implementation-size claims exceed the search evidence.** R3 §2.3 says no maintained permissive parser supports its complete Pio/UPI round-trip contract, then prescribes “~150 lines”; §4.3 says canonicalization is “~50 lines.” Absence from a survey does not prove absence, and LOC is not correctness effort. MIT DCFR-SOLVER already parses colon weights into 1,326 weights, although full grammar compatibility, UPI ordering, round-trip support and continued maintenance are **not verified**. This is a counterexample to the implied absence of permissive building blocks, not proof it satisfies the entire contract. [Parser source](https://github.com/exinori/DCFR-SOLVER/blob/main/src/range.rs)

**O08 — the reports' separate two-week plans cannot simply be added together.** R2 schedules acquisition/custom straddle/depth data; R4 schedules posterior ranges, fixed-policy response, complete-policy mixtures and a verified floor auditor; R5 schedules a desktop integration/package; R6 schedules solver validation. R4 explicitly calls its numbers proposed defaults, including 25% mixing: **these are not factual errors or calibrated population estimates**. But the combined plan has no demonstrated staffing/critical-path budget. OX-Search research does not certify R4's proposed implementation. Keep the full exploit audit outside the baseline dependency chain unless a narrow river implementation passes independent checks early. [OX-Search's actual research claim](https://proceedings.mlr.press/v235/ge24b.html)

**O09 — negative/global claims need scope limits.** R1: “No open-source solver does multiway (3+) postflop,” followed in the same paragraph by bot/generic-engine exceptions. Rewrite as: **no inspected, validated, embeddable range solver was shown to solve representative 3+ player postflop trees within the required time**. Similarly, “a precomputed flop library is required” is a proposed architecture under assumed CPU workloads, not a demonstrated universal lower bound. [OpenSpiel's 2–10-player implementation](https://github.com/google-deepmind/open_spiel/blob/master/open_spiel/games/universal_poker/universal_poker.cc)

**Evidence that should survive the adversarial review:** R2 distinguishes frequencies from arriving ranges and EV; R4 distinguishes local audited bounds from whole-game safety; R6 distinguishes six-seat environments from demonstrated six-player strength. ReBeL's apparently extreme **90 DGX-1 × 8 V100** data-generation figure is confirmed in Appendix E, not a decimal error. R6's training-versus-inference distinction is warranted. [ReBeL Appendix E](https://arxiv.org/html/2007.13544)

## 4. Blind spots and decision-relevant unresolved details

The broad requested topics are **not all omissions**: R2 §§7–8 covers straddles, depths, side pots and data validation; R4 §§4/8 and R6 §§6/8 cover multiway limits, latency and strategic testing; R1 §5.4 covers AGPL generally. The genuine omissions or materially unfinished interfaces are below.

**B01 — a human-inclusive deadline and actual deployment topology.** No report measures observing the action → entering/correcting the whole state → computation → interpreting frequencies → announcing/placing the action. R4's proposed ≤1-second input/range stage cannot substitute for a human entry trial. Distinguish a 15-second **compute** target from a 15-second **table response** target. An illustrative allocation is 4 seconds entry, 8 seconds computation, 2 seconds reading/action, 1 second reserve; this is a test target, **not verified usability**. Time a replay with six seats, multiple callers, an unusual raise and one deliberate correction. Record entry errors and stale-result incidence as well as p95 latency.

Also locate the desktop relative to the table. A home workstation is not automatically on a casino phone's LAN; R5's later LAN feature does not resolve an off-site connection, and the task's local/offline constraint may rule that out. Decide whether the baseline is used beside a permitted home/training table, on a portable client with a reachable local server, or for later hand review. This is an unresolved product requirement, not an internet-latency estimate.

**B02 — “two players able to bet” is not necessarily a heads-up pot.** Count **unfolded pot-eligible players**, separately from players still holding chips. If A is all-in and B/C keep betting, a HU side-pot decision can still affect the main pot shared with A. Treating A as folded bunching or dead money changes terminal payouts and incentives. Likewise, a three-way pot becoming HU after a fold requires ranges conditioned on the three-way history; an ordinary preflop HU chart does not recover them. Define separate coverage for genuine HU, three live ranges, all-in third player, and multiple side pots. No inspected integration is verified for the last three. [Bunching's folded-player scope](https://github.com/b-inary/postflop-solver), [Independent rules engine/pot representation](https://pokerkit.readthedocs.io/en/stable/simulation.html)

**B03 — an executable contract for off-tree wagers is missing.** R2/R6 warn about unusual sizes but no report selects and validates the translation procedure. Preserve the exact observed amount and chip accounting; never round the real pot/stacks to make a cached node fit. Example: villain bets 73 into 100; call cost is 73 and the final called pot is 246, so the no-rake/no-future-betting equity threshold is **73/246 = 29.67%**. Substitution with 50 changes it to 25%; substitution with 100 changes it to 33.33%. Range inference changes too, because betting 73 is evidence about the opponent's hand.

For the first release, prefer adding the actual wager to a bounded tree from the appropriate earlier node and solving with declared incoming ranges; otherwise return a labeled unsupported/approximate result. Rebuilding from guessed ranges remains model-conditional, not safe whole-game resolving. Define separately: incoming bet translation, posterior-range estimation, outgoing bet menu, raise-to versus raise-by, cumulative contributions, chip-denomination rounding, minimum raises and short-all-in reopening. “100% pot raise” also needs an explicit denominator, commonly the pot **after calling**. Pio's line API uses cumulative contributions, illustrating why string/percentage substitution is insufficient. [Pio tree-building semantics](https://piosolver.com/docs/upi/commands/), [Action-translation research](https://www.cs.cmu.edu/~sandholm/reverse%20mapping.ijcai13.pdf)

**B04 — coverage must be measured against the intended games, not counted in charts.** R2 does cover 100/150/200/250bb and UTG/button straddles; the missing item is an acquired, validated coverage manifest and an empirical distribution of the user's actual states. Include unequal stacks, initial versus remaining stack, ordinary/straddled units, live 4–6bb opens, limps, squeezes, re-straddles if allowed, dead posts and the actual rake/drop rule. Near a jam/minimum-raise boundary, interpolating stack buckets can change the legal action tree discontinuously. Matching SPR alone does not match ranges, rake or pot eligibility. Rank configurations by observed frequency and track unsupported requests; a hundred low-use configurations can deliver less coverage than five correct ones. [HRC's explicit cash configuration dimensions](https://www.holdemresources.net/docs/cashgame/)

**B05 — backend lifecycle and representation need tests beyond generic solver validation.** R2/R4/R6 already propose substantial testing; it would be false to say testing was ignored. Missing concrete acceptance gates include:

- **Adapter semantics:** assert hand identity/order, action-major versus hand-major arrays, native rank ordering, currency/BB units and EV reference point. In b-inary, per-action EV is `expected_values_detail`, not merely `expected_values`; the current-node normalized-weight cache must be refreshed before EV calls. Compare named combinations rather than assuming every 1,326-element vector uses the same ordering. [Actual API requirements](https://b-inary.github.io/postflop_solver/postflop_solver/struct.PostFlopGame.html)
- **Solve/lock lifecycle:** b-inary's documented lock calls are allowed after allocation **before solving** and panic on an already solved game. Implementing R4's model updates therefore needs a fresh/reinitialized compatible game or a verified engine change; R4 already acknowledges backend-dependent warm-start uncertainty. Its standard `solve()` has iteration/accuracy stops, not a wall-clock cancellation argument. Prototype `solve_step`/finalization or process replacement before promising the 15-second deadline. [Lock lifecycle](https://b-inary.github.io/postflop_solver/postflop_solver/struct.PostFlopGame.html#method.lock_current_strategy), [Solve implementation](https://github.com/b-inary/postflop-solver/blob/main/src/solver.rs)
- **Independent numerical oracle:** first verify tiny river games with explicit payoffs and an independent information-set-respecting best response/LP; then compare representative identical trees against a separate engine. Agreement between two implementations sharing evaluation code is weaker evidence. A low exploitability value computed by the same faulty traversal can agree with itself. The published TexasSolver disagreement in O02 makes this actionable.
- **Metamorphic and deadline checks:** suit/card-order permutations with inverse mapping, isomorphism on/off, compression on/off, no-rake chip scaling, save/load equivalence, board-blocked/zero-reach hands, locks and off-menu sizes. Count 1,755 alone does not prove correct orbit membership. A root average exploitability threshold does not bound error for every rare hero hand; inspect conditional action EV loss and error tails. Keep an untouched holdout set and predeclare acceptance tolerances.

Exhaustively checking all seven-card hand ranks, as R3 proposes, validates an evaluator; it does not validate chance probabilities, range normalization, betting rules, DCFR updates or action EVs.

**B06 — AGPL and phone-over-LAN require a specific boundary decision.** R1 discusses friends over a network, but R5's actual phone architecture is not reconciled with it.

- A private desktop copy may be modified and run; there is no general public-release obligation merely because AGPL code was vendored.
- A phone's HTTP interaction is remote network interaction even on a LAN; §13 is not restricted to public internet hosting. For a modified covered program, it requires a prominent opportunity for interacting users to obtain the version's Corresponding Source. Sole use by the same person does **not** create an obligation to publish to the world; there is no outside recipient to serve. Preserve an accessible source offer/archive as the concrete implementation, rather than assuming LAN traffic is exempt. [AGPL text](https://www.gnu.org/licenses/agpl-3.0.html)
- Once friends/other users use the modified service, serve the required source to those users, including relevant modifications and build material, not just a link to upstream. Distributing binaries adds the ordinary conveyance obligations. The scope is the covered combined work, not automatically every independent program on the PC. A linked solver/server and a separate browser frontend need an actual combination analysis; stdio/HTTP alone is not a guaranteed copyleft escape. GNU's FAQ treats both communication mechanics and semantics as relevant. [GNU FAQ: private changes, aggregation and network interaction](https://www.gnu.org/licenses/gpl-faq.en.html)

The exact boundary for the eventual application is **not verified**, because no application exists to inspect. This is a reason to preserve licensing/build provenance, not to write a new solver during week one. GTOpen's missing verified grant is a different problem from complying with a known AGPL license.

**B07 — table permission is separate from strategy-data permission.** R2 checks vendor live-use restrictions but no report resolves whether this assistant may be used at the intended table. This is not hypothetical: PokerStars Live's cash rules prohibit phones/tablets/laptops **while in a hand** and outside consultation. Nevada NRS 465.075 separately prohibits specified advantage-seeking strategy/probability devices in covered licensed games, subject to its stated exceptions. These examples do not establish the user's jurisdiction or venue rule; those are **not verified**. Validate the actual intended setting before calling the artifact live-ready; otherwise the same engineering can be tested in permitted simulations/study. [Cash rules, items 1 and 9](https://www.pokerstarslive.com/poker/cashgamerules/), [Nevada statute](https://www.leg.state.nv.us/nrs/NRS-465.html#NRS465Sec075)

**B08 — a cancel button and LAN bind are not complete runtime controls.** R5 mentions cancellation tokens, but the solver must actually poll them; Tokio cannot abort an already running `spawn_blocking` task. A timed-out job continuing on all cores can delay the next hand, and a late response can overwrite corrected input. Require bounded job admission, state/version IDs, no stale-result acceptance, and a tested cancellation/finalization grace period; reserve a valid fallback before the deadline. [Tokio cancellation semantics](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)

For the phone path, `0.0.0.0` binds all IPv4 interfaces, not a trusted-user identity. The reports omit pairing/authentication, request/origin validation, firewall scope, reconnect/resume and concurrent desktop/phone state ownership. These are concrete consequences of turning a private computation endpoint into a reachable service, not reasons to add a large server project to phase one.

**B09 — RTX 5080 compatibility is more specific than “supports CUDA.”** NVIDIA lists the 5080 as compute capability **12.0**, versus **8.6** for the measured RTX 3090. CUDA binaries need compatible code/PTX; older architecture-specific cubins are not interchangeable. CUDA 12.8 introduces native Blackwell support, while suitable PTX can provide forward compatibility for older builds. Check toolkit/NVRTC/driver versions, architecture flags, first-use JIT, memory peaks and CPU/GPU numerical parity. Exact compatibility and first-request latency remain **not verified**; a crate's advertised CUDA-version range alone does not establish them. [GPU capabilities](https://developer.nvidia.com/cuda/gpus), [NVIDIA toolkit/architecture matrix](https://docs.nvidia.com/datacenter/tesla/drivers/latest/cuda-toolkit-driver-and-architecture-matrix.html), [Blackwell compatibility guide](https://docs.nvidia.com/cuda/archive/12.8.0/blackwell-compatibility-guide/index.html)
